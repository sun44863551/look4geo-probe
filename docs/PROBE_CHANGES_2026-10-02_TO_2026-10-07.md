## 二、买家语言基线

### 2.1 用户规则

| 用户要求 | 参数 | 请求语言环境 |
| --- | --- | --- |
| 未明确指定买家基线 | english | en-US |
| 采用日本买家基线 | japan | ja-JP |
| 采用韩国买家基线 | korea | ko-KR |

问题本身是日文或韩文，不代表用户指定了对应买家基线。未说明时仍默认英语。

保留原始问题，不追加“请用日语回答”等指令。原有安全发送规范化仍然有效；原问题、发送版本及是否规范化继续记录。

### 2.2 自然语言调用

WorkBuddy 或 Codex 本地技能规则将明确的买家要求映射为调用参数。例如：

> 这里是 100 个日语采购问题，请仅使用 ChatGPT，采用日本买家基线执行，每题重复 3 次。

调用方应对每个问题显式传入 `buyer_baseline=japan`，保留原问题、平台选择与重复次数。

自然语言映射依赖调用方遵守本地技能说明，不是 CLI 内置的自由文本语义解析器。CLI/MCP 接收明确参数。

### 2.3 CLI 示例

以下命令在项目根目录执行：

```sh
# 日本买家
scripts/probe-local run "原始日语问题" --mode manual --platform chatgpt --buyer-baseline japan --repeats 3 --json

# 韩国买家
scripts/probe-local run "原始韩语问题" --mode manual --platform chatgpt --buyer-baseline korea --repeats 3 --json

# 不传买家参数，默认英语
scripts/probe-local run "原始问题" --mode manual --platform chatgpt --json
```

这些是使用示例，不代表对应批量任务已执行。

### 2.4 MCP 示例

`probe_run` 的参数示例：

```json
{
  "prompt": "原始日语问题",
  "mode": "manual",
  "platforms": ["chatgpt"],
  "buyer_baseline": "japan",
  "repeats": 3
}
```

MCP 提交返回任务信息，后续通过状态及结果接口获取结果。

### 2.5 结果审计

| 字段 | 位置 | 含义 |
| --- | --- | --- |
| buyer_baseline | 结果及平台尝试 | 请求的买家语言基线 |
| buyer_locale | 结果及平台尝试 | 请求语言，例如 ja-JP |
| locale_verified | 平台尝试 | 浏览器与页面语言是否通过校验 |

`buyer_baseline` 和 `buyer_locale` 是配置记录，不是验证结论。

- `locale_verified=true`：本次页面语言检查通过。
- `locale_verified=false`：检查未通过，不能纳入对应已验证基线。
- `locale_verified=null`：没有验证证据，包括旧记录或不支持验证的渠道。

旧结果不自动补标为英语基线成功。新增结果字段使用可空默认值；本次没有提升现有 schema_version，仍为 3。

### 2.6 批量任务注意事项

每条请求均应携带买家参数，检查点和样本标识应区分买家基线，不复用不同基线的历史结果。

本阶段更新了调用说明，没有将所有客户专用批量脚本统一改造成多语言执行器。固定英语脚本不能未经检查直接用于日本或韩国基线。

## 三、ChatGPT 语言设置与问答修复

### 3.1 语言设置过程

1. 在指定采样浏览器创建新会话。
2. 读取当前浏览器真实 User-Agent。
3. 在任务标签页设置 Accept-Language：英语 en-US,en；日语 ja-JP,ja；韩语 ko-KR,ko。
4. 导航到 ChatGPT。
5. 比较 navigator.language 和页面 document.documentElement.lang 与目标主语言。
6. 通过后发送问题；不通过则失败并说明不能纳入目标基线。

语言配置按会话保存，不改变其他平台任务的语言设置。代码内部分辅助函数仍保留 English 命名以兼容已有调用及测试，但实际读取会话对应的目标语言。

### 3.2 问答稳定性

- 更新 ChatGPT 输入框识别标签。
- 主回答定位到 assistant 消息中的 markdown 区域。
- 首次尝试点击发送按钮，后续可通过 Enter 尝试发送。
- 发送后检查输入框清空或生成状态，而非仅凭点击返回判定发送成功。
- 最多三次尝试；状态一直未变化时报告发送失败。

### 3.3 能证明什么

当前校验证明页面和浏览器的主语言符合目标，不保证回答正文一定采用该语言，也不保证每个信源标题都已统一语言。

语言设置不改变 IP、网络出口、国家位置或账户所在地区。不能将“日语界面”直接称为“日本当地网络采样”。

## 四、ChatGPT 采样账号隔离

### 4.1 配置

新增独立配置项：`LOOK4GEO_CHATGPT_BROWSER_ID`。

- 与共享的 `LOOK4GEO_BROWSER_ID` 分开。
- 缺失或与共享 ID 相同，ChatGPT 采样暂停。
- 不允许自动回退到日常浏览器。
- Codex 与 WorkBuddy 使用同一套本机渠道配置。

实际 ID 放在被忽略的 `config/local.env` 或本地 MCP 环境配置中；仓库模板只保存占位符。

本次真实测试绑定的 BrowserSkill 实例是 `81483588`，标签为 Look4GEO Sampling。后续若实例离线，应重新连接该 Profile，不替换其他实例。

### 4.2 隔离边界

独立 Chrome Profile 分离 cookies、登录态、历史记录等浏览器数据。真正分离账户及账户额度，还需要登录与日常账号不同的采样账号。

隔离不分离机器网络地址，也不构成操作系统级安全隔离。不要复制日常 Profile 登录数据到采样 Profile。

## 五、Gemini 相关调整

- 新增 `LOOK4GEO_GEMINI_CAMOUFOX_ONLY`，需要时限定 Gemini 只走独立 Camoufox 配置。
- 若要求 Camoufox-only 但未启用对应渠道，配置阶段报错。
- Gemini 登录入口优先选择 Camoufox 登录渠道。
- 登录成功识别同时检查输入框及 Google Account 控件。
- 调整 Flash 模式识别，兼容版本号变化及可见 Flash 文本。
- BrowserSkill Gemini 输入前增加点击聚焦。

常规配置仍可使用 BrowserSkill 主通道及 Camoufox 备用通道；Camoufox-only 则禁止回退共享 BrowserSkill 渠道。

这些改动不代表 Gemini 已具备日本/韩国买家语言验证，也不代表本阶段重新完成了全部 Gemini 采购采样。
