# ChatGPT 搜索中间态误采修复（2026-10-30）

## 发现与原因

查看当天数据库及最新 28 格客户采集日志，发现搜索进度摘要（如 Comparing / Researching / Researched）只有 18–26 字符，却被记为 succeeded；另有较长的生成中正文在检索阶段被提前接受。

在绑定的 Look4GEO Sampling 实例 81483588 中，只读回看已结束的历史会话，同一问题实际上已有 5100 字符完整答案。真实页面最终回复的祖先节点含 `data-talvt-turn-state="complete"`。旧停止按钮检测在当前 UI 的搜索/生成过程中持续返回 false，连续稳定两轮因此不足以证明回复完成。

## 修改

- 从最新回答节点所在的 turn 读取完成标记，不能使用其他历史轮次的完成状态。
- ChatGPT 实际页面必须确认当前 turn 为 complete，再进行两轮稳定检查。没有完成标记时保守等待，超时则失败，不输出假成功。
- 无论进度摘要多短、部分正文多长，都不能跳过完成确认。没有增加任意最小字数限制，也不强制插入品牌词或改写用户原题。
- 成功结果补存 conversation_url，便于复核；URL 读取失败不破坏已完成的回答。
- 不更改浏览器绑定、登录账号、Gemini Flash 或 Perplexity Search 配置。

## 验证

新增 4 项回归测试修复前均失败：稳定的短进度误成功、稳定的长片段误成功、最新轮次仍在生成、最新轮次已完成。修复后全部通过。

完整测试套件：388 passed；git diff --check 通过。

在实例 81483588 中进行一次真实问答复验，期间观察到多个中间片段暂时稳定，停止按钮检测始终为 false，但新完成确认保持 false，未提前接受。随后实际 turn 完成，完整正文稳定后返回 **5182 字符、5 条来源、failure=null**。本次诊断结果和调试证据单独保存在忽略的 work/ 目录，没有覆盖客户样本。

当天数据库快照：ChatGPT 标记成功 45、失败 3、仍为 running 4。成功标签不能直接当作有效采集数，其中至少 8 条明确只保存了搜索进度摘要。旧数据保持原样；单独输出审计清单，提醒排除这类记录，不能计为未提及。

数据库中的 4 条未终结记录尚未证明其进程归属，不自动清理，不重跑整个客户批次。现存长驻 MCP 进程启动早于本次修复，需要重新连接客户端才能载入新代码；CLI 下一次启动直接加载本机新源码。
